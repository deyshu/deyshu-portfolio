JIL NEXUS

The self-hosted database backbone — the hybrid half

Architect & developer

NEXUS is the self-owned database I built to sit underneath the church system — a self-hosted Supabase (PostgreSQL) stack running in Docker on my own machine, designed to minimise recurring cloud costs (hardware, power and internet still apply).

The point is the hybrid: the live Google Sheets system and NEXUS run side by side for safety, data is copied across and verified by matching counts, and new registrations flow Sheets → NEXUS automatically over a Cloudflare tunnel. It's the backbone designed to carry the system toward an architectural target of ~1,000,000 records across thousands of churches — a design goal, not yet load-tested.

How I handle data & access

Security & Privacy

An honest summary of what's in place today and what I'd add for a client with sensitive data — I'd rather be upfront than oversell.

In place today

  • Identity sign-in — people authenticate with their Google identity; no shared passwords.
  • Server-side permission guards — every role check runs on the server, never trusted from the browser.
  • Role-filtered access — users see only the tabs and records their role allows.
  • Tenant isolation by design — a four-tier structure keeps each church's data in its own engine.
  • Audit logging — sensitive actions (e.g. in the farm hub) record who changed what and when.
  • Hybrid redundancy — data runs in two stores in parallel (replication for safety), verified by matching record counts.
  • Privacy in this portfolio — every screenshot uses anonymous demo data; no real personal records are shown.

Added for sensitive / enterprise data

  • PostgreSQL as the system of record (not Google Sheets) for sensitive customer data.
  • Encrypted automated backups with tested restores, and encryption in transit & at rest.
  • Monitoring & alerting for uptime and errors, plus incident response steps.
  • Least-privilege access and a separate staging environment.
  • An independent security review before going live with real data.
  • Architecture & deployment documentation handed over with the system.

A clear distinction I keep in mind: running two copies of data in parallel is replication for safety — it is not the same as a backup. A separate, recoverable backup (and a tested recovery procedure) is still needed, because one bad change can affect both copies. That belongs in the right-hand column, scoped per project.

For a client project, I scope these to your requirements and start with a small pilot so you can verify security and reliability before trusting the full dataset. A downloadable technical security overview can be provided for systems involving sensitive information.
